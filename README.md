# ERP-система для Московского зоопарка

## Предметная область
Программа моделирует систему управления зоопарком, которая автоматизирует следующие процессы:
- Учет животных разных видов (львы, попугаи, змеи)
- Управление кормлением по расписанию
- Организация медицинских осмотров
- Подготовка к выставкам
- Учет сотрудников и их обязанностей
- Генерация ежедневных отчетов

## Принципы SOLID в реализации

### 1. Single Responsibility Principle (Принцип единственной ответственности)
Каждый класс имеет одну четкую зону ответственности:
- `Animal` и его наследники отвечают только за данные и поведение животных
- `FeedingService` отвечает только за кормление
- `MedicalService` отвечает только за медицинские осмотры
- `ReportGenerator` отвечает только за генерацию отчетов
- Каждый тип сотрудника (`Zookeeper`, `Veterinarian`) имеет свои обязанности

### 2. Open/Closed Principle (Принцип открытости/закрытости)
Система открыта для расширения, но закрыта для модификации:
- Для добавления нового вида животного достаточно унаследоваться от `Animal` и реализовать нужные интерфейсы
- Для добавления нового типа сотрудника нужно унаследоваться от `Employee`
- Существующий код не требует изменений при добавлении новых функциональностей

### 3. Liskov Substitution Principle (Принцип подстановки Барбары Лисков)
Наследники могут заменять родительские классы:
- Любой наследник `Animal` может использоваться везде, где ожидается `Animal`
- `Lion`, `Parrot` и `Snake` могут корректно заменять `Animal`
- Все методы базового класса работают корректно в наследниках

### 4. Interface Segregation Principle (Принцип разделения интерфейсов)
Интерфейсы узко специализированы:
- `Feedable` содержит только методы, связанные с кормлением
- `MedicalCheckable` содержит только методы медицинских осмотров
- `ExhibitionParticipant` содержит только методы участия в выставках
- Классы реализуют только те интерфейсы, которые им действительно нужны (например, `Snake` не реализует `ExhibitionParticipant`)

### 5. Dependency Inversion Principle (Принцип инверсии зависимостей)
Зависимость от абстракций, а не от конкретных реализаций:
- Сервисы зависят от интерфейсов `Feedable` и `MedicalCheckable`, а не от конкретных классов животных
- `ReportGenerator` работает с абстрактным классом `Animal`
- Внедрение зависимостей через конструкторы

## Преимущества архитектуры

### Улучшение качества дизайна:
1. **Расширяемость**: Легко добавлять новые виды животных, сотрудников и сервисы
2. **Поддерживаемость**: Код организован логически, легко находить и исправлять ошибки
3. **Тестируемость**: Классы изолированы, можно тестировать отдельно
4. **Гибкость**: Можно легко менять реализации без изменения клиентского кода
5. **Читаемость**: Четкая структура и разделение ответственностей

### Потенциальные проблемы расширения:
1. **Сложные пересекающиеся обязанности**: Если появится животное с особыми требованиями, затрагивающими несколько сервисов
2. **Изменение базовой логики**: Если потребуется изменить фундаментальные принципы работы системы для всех животных
3. **Комбинаторный взрыв интерфейсов**: При добавлении множества специализированных интерфейсов

## Как запустить проект
1. Установите Java 8 или выше
``` bash
javac -d out src/com/zoo/Main.java src/com/zoo/animals/*.java src/com/zoo/employees/*.java src/com/zoo/services/*.java src/com/zoo/interfaces/*.java src/com/zoo/reports/*.java
java -cp out com.zoo.Main
```
